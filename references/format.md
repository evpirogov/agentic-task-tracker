# Формат `.tasks/` — task-tracker/1

Локальная «база данных» задач проекта: обычные файлы в git. Этот документ — контракт
для всех, кто читает или пишет эти файлы: агент (через скилл `task-tracker`), человек
в редакторе, будущий веб-интерфейс. Эталонная реализация чтения/записи/проверок —
`~/.claude/skills/task-tracker/scripts/lib.mjs`; CLI — `tasks.mjs` там же.

## Раскладка

```
.tasks/
  README.md        этот документ (копия на момент init)
  workflow.json    статусы, переходы, гейты, словари type/priority/size, префикс ID
  items/BL-0001.md  одна задача — один файл; имя файла = id (заголовок в файле, поэтому
                   переименование задачи файл не двигает)
  docs/            длинные требования, дизайн, решения — свободный markdown; задачи
                   ссылаются на них полем docs (пути относительно .tasks/)
  project.json     (необяз.) имя, вики, страницы проекта, сканер кода — см. pipeline.md
  tech/            (необяз.) pillars.md — основы проекта, checks.md — проверки
  audits/A-0001.json  вердикты независимых аудитов (пишет только `tasks audit add`) и обходов
                      проекта хранителями (`guardian` + `marks`; пишет только `tasks guardian sweep add`)
  audits/GR-0001.json детальные ревью хранителей по находкам аудита (пишет только `tasks guardian add`)
  .cache/             сохранённые прогоны дорогих проверок (отметки хранителей), не в git
  events.jsonl     журнал изменений, только дописывается; в .gitattributes стоит
                   `merge=union`, так что параллельные ветки сливаются без конфликтов
```

## Файл задачи

```markdown

id: BL-0007
title: "Гараж: адаптивная сетка карточек"
status: backlog
type: feature
priority: p1
size: story
tags: [ui, garage]
depends_on: [BL-0005]
assignee: null
docs: [docs/garage-ui.md]
created: "2026-10-17T09:12:00Z"
updated: "2026-10-17T10:40:31Z"
---

## Description

Что и зачем. Исходная формулировка пользователя — дословно, ниже уточнения.

## Acceptance criteria

- [x] Карточки не вылезают за экран при 360px
- [ ] В альбомной ориентации 4 колонки

## Plan

## Notes

## Result

Что сделано, затронутые файлы, как проверено.
```

### Frontmatter

Строгое подмножество YAML: одна строка `ключ: значение`, значение — JSON-литерал
(`"строка"`, `null`, `true`, `3`, `["a","b"]`) или «голое» слово `[A-Za-z_][A-Za-z0-9_.-/]*`.
Списки — только в одну строку `[a, b]`. Любой YAML-парсер читает это корректно;
эталонный парсер не требует зависимостей. Даты в кавычках — чтобы YAML-парсеры не
превращали их в Date.

| поле | тип | обяз. | смысл |
|---|---|---|---|
| id | `PREFIX-NNNN` | да | совпадает с именем файла, не меняется |
| title | string | да | коротко, в повелительном/назывном виде |
| status | id из `workflow.statuses` | да | меняется **только переходом** (см. ниже) |
| type | из `workflow.types` | да | feature, bug, chore, research, idea |
| priority | из `workflow.priorities` | да | p0 (горит) … p3 (когда-нибудь) |
| size | id из `workflow.sizes` \| null | нет | объём изменений: epic (эпик/рефакторинг) › story › task (фича/баг) › tweak (правка); null — не оценён |
| tags | string[] | нет | свободные метки |
| initiative | id из `workflow.initiatives` \| null | нет | направление работы, ряд доски; одна на задачу, метка, а не родитель. Нет `initiatives` — поля нет |
| parent | id \| null | нет | **не используется** — иерархий задач нет: эпик — обычная большая задача (`size: epic`), а не папка. Поле читается только у старых данных |
| depends_on | id[] | нет | блокирующие задачи; циклы запрещены |
| assignee | string \| null | нет | кто ведёт: `user`, `agent`, имя |
| docs | path[] | нет | файлы в `.tasks/` (обычно `docs/…`) |
| origin | string \| null | нет | откуда задача: находка аудита `A-0001#2` |
| created, updated | ISO-8601 UTC | да | `updated` ставится при каждой записи |

Неизвестные поля сохраняются как есть (validate предупреждает).

### Тело

Разделы второго уровня с фиксированными английскими заголовками — по ним парсят
интерфейсы; содержимое на любом языке. Порядок: `Description`, `Decision` (необязательный:
согласованное решение — варианты, за и против, выбор), `Guardians` (необязательный: слово каждого
хранителя проекта на груминге, подраздел `### «Имя»` на хранителя, пишет `tasks guardian say`; см.
guardians.md), `Acceptance criteria`, `Plan`, `Notes`,
`Result`, `Wiki` (необязательный: черновик правок вики — какой файл, что поменять; в саму вики
переносится только на переходе в done, см. pipeline.md). Свои разделы можно добавлять. Пустой раздел оставляют
заголовком. Критерии приёмки — чек-лист `- [ ]` / `- [x]`; номер пункта = его порядок
среди чек-лист-строк раздела (с 1). HTML-комментарии считаются пустотой.

## Статусы и переходы (`workflow.json`)

- `statuses[]`: `{id, title, category, hold?}`; `category` ∈ `todo | active | done`; `hold: true` — отложенные задачи (icebox): `next` их не предлагает, брать их можно только по слову пользователя
  (колонки доски группируются по ней; `done`-категория = задача закрыта, в т.ч. `cancelled`).
- `initial_status` — куда попадает новая задача.
- `sizes[]` (необязательно): `{id, title}` от самого большого к самому маленькому — шкала объёма
  изменений для поля `size`. Нет `sizes` — поля `size` у задач нет.
- `initiatives[]` (необязательно): `{id, title, goal?, closed?}` в порядке рядов доски — направления
  работы для поля `initiative`; закрытая уходит с доски, её задачи её сохраняют. Правятся только
  `tasks initiative …`.
- `aspects[]` (необязательно): `{tag, title}` — теги сквозного качества (например, `perf`):
  фильтр поверх всех рядов. Правятся `tasks aspect …`.
- `transitions[]`: `{from, to, gates?}`; `from`/`to` — id, массив id или `"*"`.
  Действует **первый** подходящий переход. Нет перехода — смена статуса запрещена.
- `gates{}`: именованные проверки. Общие поля: `kind`, `message?`, `if_types?`, `if_tags?`
  (гейт применяется только к задачам с таким типом/тегом).

| kind | параметры | проходит, если |
|---|---|---|
| section_nonempty | section | раздел не пуст |
| checklist_nonempty | section | в разделе есть хотя бы один `- [ ]` |
| checklist_complete | section, allow_empty? | пункты есть и все отмечены; с `allow_empty: true` пустой список тоже проходит |
| field_set | field | поле задано / список не пуст |
| field_in | field, values | значение поля из списка (например, короткий путь только для size tweak) |
| deps_done | also? | все `depends_on` в статусах категории done (или в статусах из `also`, например `qa`: работа сделана, ждёт аудита) |
| children_done | — | (устарел, иерархий нет) все задачи с `parent` = эта закрыты |
| note_required | — | при переходе дана заметка (причина) |
| by_user | — | переход делает пользователь (`--by user`) — агент ставит его, только когда пользователь сам попросил |
| attestation | prompt, questions[], min_length (40) | дан письменный вердикт по вопросам (`--attest gate=…`), не короче min_length |
| command | run, timeout_s (300) | shell-команда из корня проекта завершилась с кодом 0 |
| audit | since? | записан аудит (`audits/`), где у задачи `verdict: pass`, — после входа задачи в текущий статус, а с `since: "work"` — после конца работы над ней (последний выход из in_progress); и каждая его находка в зоне хранителя (`guardian`) принята этим хранителем (последнее ревью `GR-…` — `accept`) |
| guardians_asked | section? | у каждого хранителя проекта (`project.json` `guardians`) есть непустой подраздел `### «Имя»` в разделе `Guardians` (по умолчанию); в проекте без хранителей проходит сам |

`command`-гейты запускаются только когда прошли все остальные гейты перехода.
Обход гейтов (`--force`) требует заметки и записывается в журнал как `forced`.

## Журнал `events.jsonl`

Одна JSON-строка на событие, только дописывание, порядок — по `ts`.

```json
{"ts":"2026-10-17T09:12:00Z","task":"BL-0007","type":"created","by":"user","to":"backlog","title":"…"}
{"ts":"…","task":"BL-0007","type":"status","by":"agent","from":"in_progress","to":"review","attest":{"architecture_review":"1. pass — …"},"checks":{"i18n":"ok"}}
{"ts":"…","task":"BL-0007","type":"edit","by":"agent","changes":{"priority":["p2","p1"]}}
{"ts":"…","task":"BL-0007","type":"section","by":"agent","section":"Result","mode":"set"}
{"ts":"…","task":"BL-0007","type":"acceptance","by":"agent","check":[1,2]}
```

Общие необязательные поля: `session` — id сессии Claude Code, сделавшей изменение;
`head` (у `status`) — коммит, на котором стояла работа (`+` — с незакоммиченными правками).
Типы: `created`, `status` (`from`, `to`, `note?`, `attest?`, `checks?`, `forced?`),
`audit` (`audit`, `verdict`; `by: auditor`), `guardian` (`guardian`; слово на груминге — `mode: say`,
ревью — `review`, `finding`, `verdict`; `by: guardian`),
`edit` (`changes: {поле: [было, стало]}`), `section` (`section`, `mode: set|append`),
`acceptance` (`add?`, `check?`, `uncheck?`, `remove?`). `by` — `user` или `agent`.
Файл задачи — текущее состояние, журнал — история; при ручной правке файла событие
не появится, поэтому пишущие инструменты обязаны дописывать журнал.

## Правила для пишущих инструментов

1. Статус меняется только через переход с проверкой гейтов (lib `moveTask`).
2. Новый id = максимум по `items/` и журналу + 1; файл создаётся эксклюзивно (`wx`),
   при коллизии берётся следующий — безопасно для параллельных сессий.
3. Запись файла — через временный файл и rename; `updated` обновляется.
4. Каждое изменение — событие в `events.jsonl`.
5. После ручных правок — `tasks.mjs validate`.
6. Экспорт для интерфейсов: `tasks.mjs export` → `{format, workflow, tasks[], events[]}`;
   у задачи в экспорте есть `sections{}` и разобранный `acceptance[]`.

Версия формата — поле `format` в `workflow.json`. Несовместимые изменения меняют
`task-tracker/N`.

# Хранители: владельцы зон

Общий принцип трекера; конкретных хранителей проект регистрирует у себя, в своих MD-файлах (уставах).
Проект без хранителей работает как раньше: всё ниже включается только записью `guardians` в
`.tasks/project.json`.

## Кто такой хранитель

Хранитель — отдельный разработчик, ответственный за одну зону проекта. Зона — это не файлы, а то,
как во всём проекте правильно делать одну вещь (например, порядок работы за кадр или где модель в
бою). Зона — его собственность: только он определяет, как делать правильно. Все, кто правит код, —
коллеги из «других отделов»; к своей зоне он относится ревностно и говорит им, как надо на самом
деле, чтобы ответственность не размывалась.

- Правка может быть где угодно в коде. Хранитель находит её и говорит, как правильно сделать через
  **общее место** — код владельца зоны и его двери (функции, методы, заранее сказано, кому какая).
- Если общее место надо доработать, **решение, как именно, принимает хранитель**: что добавить, где,
  какая у этого дверь, кто её открывает. Исполнитель не дорабатывает общее место по-своему.
- Его устав меняется только с «да» пользователя: хранитель предлагает, пользователь решает.
- Хранитель — агент, который читает код и понимает свою зону. Детерминированная проверка его не
  заменяет: она ловит только те обходы, что в неё заранее записаны, а способов обойти и накосячить
  бесконечно много («это как ворота в чистом поле… Это видимость! А не реальная проверка!» —
  пользователь, 2026-11-11). Поэтому у хранителя нет автоматической проверки и в сборке его нет.

## Устав: формат

Один файл на хранителя, `<charters>/<id>.md` (папка — `guardians.charters` в `project.json`).
Обязательные поля и разделы проверяет `tasks validate`.

```markdown
---
id: frame              # как в имени файла; им хранителя называет аудитор ("guardian": "frame")
name: Кадр             # как его зовут люди: «Кадр»
pillar: frame          # основа проекта (.tasks/tech/pillars.md), если есть
---

# Хранитель «Кадр»

## Кратко
2–4 строки: зона, общее место, главное правило. Это идёт в каждый бриф аудитора.

## Зона
Что значит «делать эту вещь правильно» во всём проекте; какой код где угодно в неё попадает.

## Общее место и двери
Владелец (файлы), его двери и кто какую открывает.

## Правила
Каждое — с причиной (почему иначе нельзя). Если у проверки есть id правил — те же id.

## Признаки обхода
Как выглядит обход общего места: по ним аудитор и исполнитель узнают зону.

## История багов
Баги, которые были из-за обходов (задачи), и известный долг.
```

Необязательные разделы: «Проверка» (что видит и чего не видит автоматическая проверка), свои.

## Регистрация в проекте

```json
"guardians": {
  "charters": "dev/guards"
}
```

- `charters` — папка уставов от корня проекта (`README.md` в ней не устав).
- `check` — устарело, не использовать (хранитель — агент, см. выше; отметки по файлам ставит он
  сам, процесс 3). Трекер ещё умеет показать результат такой команды в `tasks code`, если она задана: Печатает JSON (код выхода не важен):

```json
{
  "files": {
    "src/x.js": {
      "frame": { "mark": "broken", "violations": [
        { "rule": "frame-pass", "line": 653, "where": "render", "title": "…", "message": "почему",
          "debt": { "task": "AB-0197", "why": "…" } }
      ] },
      "poses": { "mark": "clean", "violations": [] }
    }
  },
  "errors": ["проверка сама сломана: дверь пропала, проба не поймана…"]
}
```

`mark`: `home` (файл владельца), `clean`, `broken`. `debt` — известное нарушение с задачей, которая
его закроет (`task: null` — решение за пользователем); `null` — новое. Ключи — `id` уставов.

Трекер запускает проверку из `tasks code` и `tasks audit brief`, хранит результат в
`.tasks/.cache/guardians.json` (не в git) по ключу кода (хэши файлов сканера, `project.json`,
уставы) и запускает снова, только когда код изменился. Админка показывает сохранённый результат
(помечает устаревшим) и сама проверку не запускает.

## Где видны отметки

Отметки по файлам ставит сам хранитель, когда читает весь проект (процесс 3): `владелец`, `✓` или
`✗` с находками. Отметка держится для той версии файла, на которой её поставили: файл изменился —
она «устарела» и файл снова считается непрочитанным этим хранителем.

- `tasks code` — по хранителю: сколько файлов прочитано на нынешней версии (и сколько изменились
  после), сколько нарушают, сколько открытых находок и сколько из них уже задачи; дата последнего
  обхода. Красные файлы перечисляют находки с именем хранителя (`[structure] «Кадр»: … (A-0031#2 → AB-0210)`).
- `tasks code <файл>` — строка `guardians: «Кадр» ✗ 1, «Позы» ✓` (`не читал`, `(устарело…)`) и
  пояснение каждого хранителя к отметке.
- `tasks guardian sweep` — то же по хранителям целиком и что осталось прочитать.
- `tasks audit brief` — раздел «The guardians» (кратко каждый устав, как отдавать находку
  хранителю) и у каждого файла в охвате строка `guardians:` с отметками; находки хранителей — среди
  открытых находок.
- Админка, раздел «Код»: у файла строка «Хранители» (отметка каждого, подсказка — чей обход, когда,
  пояснение), у находки — строка «Хранитель». Открытая находка хранителя делает файл красным, как
  любая находка.

## Процесс 1: груминг (backlog → todo)

После черновика `Decision`, до показа пользователю:

1. Каждому хранителю проекта — своя задача на мнение: **свежий агент** (не fork) на хранителя.
   ```bash
   tasks guardian brief <хранитель> AB-N --out <scratch>/g-<id>.md --answer <scratch>/g-<id>-answer.md
   ```
   В брифе: устав целиком, слова пользователя, черновик решения (`--draft файл`, иначе `Decision`).
   Промпт агенту: «Прочитай бриф <путь> и выполни его в точности». Ничего от себя о решении.
2. Хранитель решает, его ли это зона:
   - не его — отвечает `не моя зона` и одной фразой почему;
   - его — как правильно в его зоне: какое общее место и какие двери, что в черновике не так,
     как доработать общее место (его решение), что поменялось бы в уставе (предложение), как
     проверить.
3. Ответ — в ТЗ задачи как есть: `tasks guardian say AB-N <хранитель> --file <ответ>`
   (раздел `## Guardians`, подраздел `### «Имя»` на хранителя; повторный ответ заменяет прежний).
   Если ответ меняет решение — поправь `Decision`; слова хранителя не переписывай.
4. Гейт `guardians_asked` на `backlog → todo`: у каждого хранителя проекта есть непустой подраздел.
   В проекте без хранителей проходит сам.
5. Пользователь видит решение вместе со словами хранителей и даёт «да».

Исполнитель читает `## Guardians` как часть решения: preflight сверяет и его.

## Процесс 2: Arch QA (qa → done)

1. **Один аудитор** по брифу `tasks audit brief` — как обычно. В брифе — список всех хранителей
   (кратко их уставы), их отметки по файлам и слова хранителей на груминге.
2. Нашёл проблему в зоне хранителя (обход общего места, нарушенное правило, что-то, что ему не
   нравится там) — находка с `"guardian": "<id>"` и `"tasks": [...]` (к каким задачам аудита она
   относится). Как дорабатывать общее место, аудитор не решает. Задачу держат только её находки:
   без `"tasks"` находка относится к задачам, чьи коммиты (номер задачи в начале темы) меняли её
   файлы кода, а если таких нет — ко всем задачам аудита.
3. Каждую такую находку — **вызванному хранителю на детальное ревью**, свежий агент:
   ```bash
   tasks guardian review A-0012#3 --out <scratch>/r.md --verdict <scratch>/r.json
   ```
   В брифе: устав, находка, задачи аудита (слова пользователя, решение, что хранитель сказал на
   груминге), отметки проверки по файлам находки. Вердикт — JSON: `accept` | `reject`, `summary`,
   у `reject` — `how` (как правильно через общее место), `common_place` (его решение, как
   дорабатывать), `charter` (предложение к уставу), `check` (правило или проба, которой не хватило).
4. `tasks guardian add --file <scratch>/r.json` — вердикт записывается как есть
   (`.tasks/audits/GR-0001.json`), не править.
5. Гейт `audit` (qa → done): аудит с pass **и** все вызванные хранители приняли (последний вердикт
   по каждой находке с `guardian` — `accept`). `reject` → `tasks move AB-N in_progress --note
   "GR-0003: …"`, исправить, снова аудит.

Предложения хранителей к уставу и решения о доработке общего места — пользователю: устав меняется
по его «да» (как вики — на `qa → done`, черновиком в `Wiki` задачи).

## Процесс 3: аудит всего проекта (только по запросу пользователя)

Пользователь просит проверить весь проект («проведи аудит всего проекта», «проверь все файлы
хранителями»). Тогда каждый файл по очереди читает каждый хранитель проекта — свежий агент на пачку
файлов, со своим уставом. Это не автоматическая проверка: отметки ставит агент, который прочитал файл.
Сам по себе, на каждую задачу или в сборке этот обход не запускается. Общий аудитор по областям
(pipeline.md, «Базовый аудит кода») идёт рядом, как раньше: хранитель судит только свою зону.

1. План: `tasks guardian sweep` — по хранителю: сколько уже прочитано, сколько пачек и строк
   осталось. Пачки — файлы сканера в порядке областей `project.json`, до ~8000 строк в пачке
   (`--lines`). `--rest` — только файлы, которые хранитель ещё не читал на их нынешней версии
   (после первого обхода — основной режим); `--guardians a,b`, `--area id`, `--files a,b` сужают.
2. Брифы: `tasks guardian sweep [--rest] --dir <scratch>/sweep` пишет `<хранитель>-<k>.md` на
   каждую пачку (устав целиком, файлы пачки по порядку, его открытые находки на них) и путь вердикта
   `<хранитель>-<k>.json`; рядом `sweep.json` — какие файлы в какой пачке.
3. На каждый бриф — **свежий агент** (не fork), модель как у основного агента, промпт: «Прочитай бриф
   <путь> и выполни его в точности». Ничего от себя. Пачки независимы: агентов можно запускать
   параллельно (сколько разрешил пользователь).
4. Хранитель читает файлы по одному, целиком, и на каждый ставит отметку:
   - `home` — файл его общего места (всё равно судит по уставу);
   - `clean` — в его зоне здесь ничего не сделано неправильно;
   - `broken` — его вещь сделана мимо общего места или нарушено правило: на каждое нарушение
     находка — где (файл:строки), что и почему так нельзя (правило устава), как правильно через
     общее место (`fix`: какая дверь, чей код; доработка общего места — его решение), `rule`.
   Его прежние открытые находки на этих файлах: ещё на месте — отметка `broken` с id в пояснении;
   исправлены — id в `resolves`.
5. `tasks guardian sweep add --file <scratch>/sweep/<хранитель>-<k>.json` — вердикт записывается как
   есть (`.tasks/audits/A-0031.json`, с `guardian` и `marks`; трекер добавляет время, сессию, коммит и
   хэш каждого отмеченного файла). Трекер проверяет только форму: отметка одна из трёх, у `broken`
   есть находка или пояснение, находка — в зоне этого хранителя и с `fix`. Файлы пачки без отметки он
   называет: они остаются непрочитанными, их заберёт `--rest`. Не править, не смягчать; не согласен —
   новый агент на ту же пачку.
6. Нарушение — находка хранителя: `tasks audit task A-0031#2` заводит из неё задачу в backlog
   (Description — слова хранителя: что нарушено и как правильно через общее место). Находка
   закрывается как любая: задача done, отмена с `wontfix` или `resolves` следующего обхода.
   Детального ревью (`guardian review`) у неё нет: это уже слово самого хранителя.

Предложения хранителя к уставу и решения о доработке общего места, если они есть в находках, —
пользователю, как в процессе 2.

## Экономия

- Обход всего проекта — только по просьбе пользователя. Стоит он «строки кода × хранители»:
  на каждого хранителя ≈ строки / 8000 агентов. Повторный — `--rest`: только изменённое и непрочитанное.

- Хранитель, которому явно не его зона, отвечает одной строкой: такой опрос дешёвый.
- Детальное ревью — только по находке аудитора в зоне хранителя, не на каждую задачу.
- Повторяющийся обход зоны — строка в «Признаках обхода» и «Истории багов» устава: хранитель-агент читает её на каждом ревью.

# Процесс pipeline: груминг, исполнение, приёмка, независимый аудит

Шаблон `templates/workflow.pipeline.json` (`tasks init --template pipeline`). Для проектов, где
важна устойчивость архитектуры: каждую новую функцию сначала проверяем на то, как она ляжет на
основы проекта. В конце работы задачу проверяет независимый аудитор, которому не рассказали,
как её делали.

```
icebox ⇄ backlog → todo → in_progress → review → qa → done      (+ cancelled из любого)
                    ↑ груминг   ↑ preflight    ↑ приёмка  ↑ независимый аудит
                    (+ хранители)                         (+ вызванные хранители)
```

Если в проекте есть хранители (владельцы зон, [guardians.md](guardians.md)), на груминге каждый
говорит своё слово в ТЗ, а на Arch QA находку в его зоне аудитор отдаёт ему на детальное ревью. В
аудите всего проекта (по просьбе пользователя) каждый хранитель читает каждый файл.

Короткий путь для правки (`size: tweak`): `in_progress → done` после Result и самопроверки, без
приёмки и отдельного аудита. Это мелкий баг или подстройка, которые пользователь не увидит. Их
файлы проверит следующий пакетный аудит изменённого кода (раздел 4). Всё видимое пользователю
идёт через review.

## Экономия: где тратить агентов

Каждый агент — это токены и время пользователя. Правила:

- **Зелёный проект — нет открытых high и medium.** `low` ждут, пока рядом не пойдёт работа:
  отдельных заходов ради них нет. Аудитор сообщает не больше пяти `low`.
- **Аудит — только изменённого**, пакетом: `tasks audit brief <задачи> --since <коммит
  прошлого аудита>`. В охват входят изменённые файлы, их вызывающие идут контекстом. Основы
  в брифе полностью только те, которых касается охват, остальные — заголовком. Один аудитор
  на пакет. Делить по областям имеет смысл, только если пакет больше ~60 файлов.
- **Модель по работе.** Проектирование, аудит, сложные правки — сильная модель. Механическое
  (учёт задач, правка по готовой находке с точным местом, прогон сценариев, снимки) — модель
  подешевле (`model: sonnet` у Agent).
- **Не больше двух исполнителей сразу.** Правки одних файлов — по очереди.
- **Повторяющаяся находка становится проверкой.** Если аудит дважды ловит один вид ошибки,
  заведи правило сканера (`project.json` → `patterns`) или dev-сценарий с exit 1. Тогда её
  ловит команда, а не агент.
- **Проверка по риску.** Невидимая правка: сборка и сценарии своей области. Изменение вида:
  снимки до и после. Изменение боя или симуляции: повторяемость (`RUNS=2`).
- **Сначала проектирование, потом код.** Неясное решение — вопрос пользователю до исполнителя,
  а не переделка после аудита.

## Файлы проекта

- `.tasks/project.json`:
  - `name`;
  - `wiki: {dir, home}` — вики для людей, обычно `docs/` и `README.md` как оглавление;
  - `tech: {pillars, checks}` — пути внутри `.tasks/`;
  - `pages: [{id, title, url, start, short?, icon?, embed?}]` — страницы проекта в админке
    (раздел rail, iframe на всё место справа), например лаборатория с dev-сервера; `start` —
    чем её запустить, `short` — подпись в rail (иначе первые буквы), `icon` — `lab`, `game` или
    `page`, `embed: false` — не добавлять к адресу `?embed=1`;
  - `code: {include, exclude, ext, entries, areas[{id,title,paths}], patterns[{id,re,allow|max,message}], dup}`;
  - `guardians: {charters}` — хранители проекта: папка уставов (`<id>.md` на хранителя),
    [guardians.md](guardians.md); `check` устарел. Нет записи — нет хранителей.
  - `theme` — путь (от корня проекта) к CSS с цветами проекта поверх токенов админки
    (`--bg`, `--panel`, `--accent`… светлые и тёмные), например общий файл с инструментами
    проекта; админка отдаёт его как `/theme.css`.
- `.tasks/tech/pillars.md` — основы проекта, раздел на каждую: `## id — Название`, под ним
  правила и где в коде.
- `.tasks/tech/checks.md` — известные проблемы, которые ищут самопроверка и аудитор
  (z-fighting, дубли, бюджеты…).
- `.tasks/audits/A-0001.json` — вердикты аудиторов. Пишутся только `tasks audit add`, не
  правятся.

## Журнал решений

Задача — место, где потом ищут, почему сделано так, а не в истории чата.

- **Description** — слова пользователя дословно.
- **Decision** — что решили:
  - на какие основы влияет и как;
  - варианты с за и против;
  - выбранный вариант и почему;
  - каких данных не было.
- **Notes** — каждое следующее сообщение пользователя по задаче дословно
  (`tasks note AB-1 --by user "…"`, пишется цитатой) и выводы агента: на старте (как понял,
  с чего начинаю) и по итогу.
- **Сессии.** Каждое событие журнала само несёт id сессии Claude Code и коммит. Админка
  показывает сессии задачи и открывает их расшифровку.

## 1. Груминг: backlog → todo

1. Разобраться в коде, который задача затронет. Сверить с основами (`tasks code`, pillars.md).
2. `tasks section AB-N Decision --stdin` — влияние на каждую затронутую основу: ложится на
   каркас как есть, или сначала нужен небольшой рефакторинг (тогда он часть решения или
   отдельная задача). Варианты, за и против, выбор и почему.
3. Эпик: шаги чек-листом в `Plan`. Пункты эпика делаются без отдельного одобрения каждого.
4. Хранители (если есть в проекте): каждому — свежий агент с брифом `tasks guardian brief
   <хранитель> AB-N`; ответ («не моя зона» или как правильно в его зоне и как доработать общее
   место) — в ТЗ как есть: `tasks guardian say AB-N <хранитель> --file …`. Ответ меняет решение —
   поправь `Decision`. Гейт `guardians_asked` ([guardians.md](guardians.md), «Процесс 1»).
5. Показать решение (со словами хранителей) пользователю. После его явного «да»:
   `tasks move AB-N todo --by user --note "«его слова»"`.

## 2. Исполнение: todo → in_progress → review

Задачу из todo может взять субагент. Бриф субагенту:
- id задачи;
- команда `tasks show AB-N`;
- путь к скилу;
- требование пройти preflight;
- не расширять объём;
- при расхождении вернуть вопрос и остановиться.

- **committed** (гейт выхода из in_progress в review или done): код вне `.tasks/` закоммичен. Коммит
  перехода — конец отрезка работы задачи; по отрезкам аудит берёт её файлы.
- **preflight** (аттестация при взятии). Исполнитель сверяет решение с кодом сейчас.
  - Если что-то не сходится (файлов нет, решение противоречит коду или основам, из слов
    пользователя что-то потеряно): `tasks move AB-N backlog --note "вопрос"`, а основному
    агенту вернуть вопрос.
  - Основной агент несёт его пользователю.
- **По ходу.** Отмечать `Plan`, писать `note` о решениях. Работа вне рамок задачи становится
  новой задачей в backlog.
- **self_check** (аттестация автора). Вопросы целостности плюс прогон проверок из
  `checks.md`. Это не аудит: автор проверяет себя, чтобы не отдавать на приёмку сырое.

### Вики — источник правды

Вики проекта (`project.json` → `wiki.dir`, обычно `docs/`) — то, что пользователь проверил и
принял. Агент опирается на неё и на код; своих непринятых правок источником не считает.
- По ходу работы вики не правят. Что в ней должно поменяться, пишут черновиком в раздел задачи
  `Wiki` (`tasks section AB-N Wiki --stdin`): файл → что поменять, словами решения, принятого
  пользователем.
- В вики черновик переносится только на переходе `qa → done`, после приёмки пользователем и
  аудита с pass (и после исправлений по находкам) — аттестация `wiki_applied`.
- Черновики `Wiki` других задач (ещё не done) — не источник правды: о решениях судят по вики,
  о том, как устроено сейчас, — по коду.
- Короткий путь правки (`tweak`) вики не трогает: правка, меняющая вики, — не правка.
- Исключения проекта (например, записи слов пользователя дословно) перечисляет его CLAUDE.md.

## 3. Приёмка: review → qa

- Пользователь смотрит и комментирует. Каждый комментарий записывается дословно
  (`note --by user`).
- Если есть правки: `review → in_progress` с причиной.
- Когда пользователь сказал «принимаю»: `tasks move AB-N qa --by user --note "«…»"`.
- Приёмка идёт до аудита, чтобы не тратить рефакторинг на то, что пользователь откатит.

## 4. Независимый аудит: qa → done

Аудит можно делать на одну задачу или пачкой на все задачи в qa (как проверку релиза).

1. Собрать бриф:
   ```bash
   tasks audit brief AB-3 AB-5 --title "Релиз: …" --out <scratch>/brief.md --verdict <scratch>/verdict.json
   ```
   - В бриф входят:
     - слова пользователя, Decision, критерии;
     - файлы, изменённые в отрезках работы каждой задачи (от коммита, на котором она вошла в
       in_progress, до коммита, на котором вышла; гейт `committed` не выпускает задачу из работы с
       незакоммиченным кодом); после аудита задачи — её отрезки после него и всё, что изменилось с
       коммита этого аудита (правка после вердикта видна, где бы задача ни стояла). Код
       аудитор читает таким, какой он сейчас: коммиты говорят только, какие файлы трогала задача;
     - основы и проверки проекта;
     - сигналы сканера;
     - открытые находки по этим файлам;
     - раздел Wiki задачи: что попадёт в вики на done, аудитор проверяет, что он говорит правду о коде.
   - если в проекте есть хранители: их список (кратко уставы), их отметки по файлам и что они
     сказали на груминге;
   - **Не входят** Plan, Notes и Result: мнение авторов о своей работе влияло бы на вердикт.
2. Запустить **нового** агента (не fork: у него не должно быть контекста работы):
   - модель как у основного агента;
   - промпт: «Прочитай бриф <scratch>/brief.md и выполни его в точности. Вердикт — JSON в
     <scratch>/verdict.json». Ничего не добавлять о том, как делали.
3. `tasks audit add --file <scratch>/verdict.json`.
   - Вердикт записывается как есть: не править, не смягчать.
   - Не согласен — запусти повторный аудит со свежим агентом, а не редактируй.
   - Находка с `"guardian"` (в зоне хранителя) — тому хранителю на детальное ревью: `tasks guardian
     review A-0007#2 --out … --verdict …` → свежий агент → `tasks guardian add --file …` как есть
     ([guardians.md](guardians.md), «Процесс 2»).
4. По задачам:
   - **pass** → перенести раздел `Wiki` задачи в вики, затем
     `tasks move AB-N done --attest wiki_applied="…"`. Гейт `audit` сам проверит, что после
     входа в qa был аудит с pass и что все вызванные им хранители приняли (`accept`); находку,
     у которой есть своя задача (её `origin`, например по слову пользователя), держит та задача, а не эта;
     у той задачи хранитель этой находки принимает её заново после её аудита.
   - хранитель **не принял** (`reject`) → `tasks move AB-N in_progress --note "GR-0003: …"`:
     сделать, как он сказал, через общее место; снова review (если менялось видимое) и аудит.
   - **fail** → `tasks move AB-N in_progress --note "находки A-0007#1, #3"`. Исправить, снова
     пройти review (если менялось видимое) и аудит.
5. Находки, не связанные с задачей, — это прежний долг: `tasks audit task A-0007#2` заводит их
   в backlog.
   - Находка закрывается одним из трёх способов:
     - её задача выполнена (`done`);
     - задача отменена с меткой `wontfix` — это решение пользователя не чинить;
     - следующий аудит перечислил её в `resolves`.
   - Задача, отменённая по другой причине (например, поглощена эпиком), находку не закрывает.

**Пакетный аудит изменённого** — основной режим после первого аудита:
`tasks audit brief AB-3 AB-5 --since <коммит> --title "Пакет: …"`.

**Базовый аудит кода** (без задач) заполняет техническую вики.
- `tasks audit brief --files a.js,b.js --title "Аудит: <область>"` по областям из
  `project.json`.
- Несколько аудиторов можно запустить параллельно, по аудитору на область.
- Есть хранители — **аудит всего проекта** (только по просьбе пользователя): рядом с аудиторами
  областей каждый хранитель читает каждый файл, пачками (`tasks guardian sweep --dir …` → свежий
  агент на пачку → `tasks guardian sweep add` как есть; нарушения — находки, задачи из них —
  `tasks audit task`). Порядок — [guardians.md](guardians.md), «Процесс 3».

## Техническая вики

Админка, раздел «Код»: состояние каждого файла.
- **Красный.** Открытая находка, вердикт не «ok» на этой версии файла, нарушенное правило
  проекта (`patterns`), нарушение хранителя (новое или долг) или большая копия кода.
- **Жёлтый.** Аудита не было, или файл изменён после него.
- **Зелёный.** Проверен и с тех пор не менялся.

Агенту перед работой в области: `tasks code`, `tasks code <файл>`. Там видно, что уже известно
плохого и где лежат копии.

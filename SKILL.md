# task-tracker

Данные живут в проекте: `.tasks/` (items/*.md, events.jsonl, workflow.json, docs/).
Формат — [references/format.md](references/format.md) (он же копируется в `.tasks/README.md`).
Все изменения — **только через CLI**, он проверяет переходы, гейты и пишет историю:

```bash
node ~/.claude/skills/task-tracker/scripts/tasks.mjs <command> …
```

(ниже `tasks` = эта команда; запускать из корня проекта или глубже — `.tasks/` ищется вверх).
Руками файлы в `.tasks/items/` не правь: потеряется журнал. Если всё же правил — `tasks validate`.

## Команды

| что | команда |
|---|---|
| завести трекер | `tasks init [--prefix T]` |
| завести с процессом pipeline | `tasks init --template pipeline [--prefix AB]` — см. [references/pipeline.md](references/pipeline.md) |
| одна задача | `tasks add "Заголовок" --type bug --priority p1 --size task --tags ui,garage --desc "…" --ac "критерий" --ac "ещё" [--deps BL-3] [--status icebox] --by user` |
| пачка задач | `tasks add --stdin --by user <<'EOF'` JSON-массив `EOF` (поля ниже) |
| список / доска / следующее | `tasks list [--status …] [--tag …] [--all] [--json]`, `tasks board`, `tasks next` |
| карточка + история | `tasks show BL-7` (id можно писать `7`, `bl-7`, `BL-0007`) |
| проверить переход заранее | `tasks check BL-7 review` — покажет, какие гейты не пройдены и вопросы аттестаций |
| перевести | `tasks move BL-7 <status> [--note "…"] [--attest gate="…"]` |
| поля | `tasks edit BL-7 --priority p0 --size story --initiative ground --add-tag perf --deps BL-3,BL-4` |
| инициативы | `tasks initiative [list]`, `initiative add <id> <Название> [--goal …] [--before id]`, `edit`, `order <id> <id>…` (порядок рядов сверху вниз), `close\|open`; аспекты: `tasks aspect add perf Скорость`; доска рядами `tasks board --lanes` |
| разделы | `tasks section BL-7 Plan "…"`, `tasks section BL-7 Result --stdin <<'EOF' … EOF`, `--append` дописывает, `--replace` переписывает непустой раздел (без флага — ошибка), `--remove` убирает раздел; внутри раздела заголовки только `###` |
| заметка | `tasks note BL-7 "что выяснил"` (датированная строка в Notes); слова пользователя — `--by user` (дословно, цитатой) |
| критерии | `tasks ac BL-7 --add "…"`, `--check 1,2`, `--uncheck 3`, `--rm 4` |
| журнал | `tasks history [BL-7]`, проверка формата `tasks validate`, всё в JSON `tasks export` |
| админка в браузере | `tasks serve [--port 4747] [--open]` — задачи, вики, код, страницы проекта, сессии; только просмотр |
| состояние кода | `tasks code [файл] [--red\|--stale] [--json]` — красное/жёлтое/зелёное, находки, копии, правила |
| аудит | `tasks audit brief [ids…] [--files …] [--since <коммит>] --out brief.md --verdict v.json`, `audit add --file v.json`, `audit list\|show A-1`, `audit task A-1#2` |
| хранители | `tasks guardian [list]`; груминг: `guardian brief <хранитель> <id> --out b.md --answer a.md`, `guardian say <id> <хранитель> --file a.md`; Arch QA: `guardian review A-1#2 --out b.md --verdict v.json`, `guardian add --file v.json`, `guardian show GR-1` — см. [references/guardians.md](references/guardians.md) |
| аудит всего проекта хранителями (по просьбе пользователя) | `tasks guardian sweep [--rest] [--guardians a,b] [--area id]` (что прочитано, пачки), `guardian sweep … --dir <scratch>/sweep` (бриф на пачку), `guardian sweep add --file v.json` — [guardians.md](references/guardians.md), «Процесс 3» |

Коды выхода: 0 — ок, 1 — ошибка, 2 — переход заблокирован гейтами (вывод говорит, чего не хватает).

Поля JSON для `add --stdin`: `title` (обяз.), `type`, `priority`, `size`, `initiative`, `tags[]`, `description`,
`acceptance[]`, `plan`, `notes`, `depends_on[]`, `docs[]`, `status`, `by`,
`ref`. `ref` — локальное имя внутри пачки: `"depends_on": ["@schema"]` ссылается на задачу,
созданную выше в той же пачке.

## Инициативы

Инициатива — направление работы проекта (земля, модели, тени…): у задачи ровно одна, на доске это
ряд (вид «Инициативы»). Это метка, не задача-родитель: иерархий нет. Список — в
`.tasks/workflow.json` (`initiatives`), правится только `tasks initiative …`; `tasks initiative`
покажет, какие есть.

Как выбрать, заводя задачу (`--initiative`, в пачке — поле `initiative`):
- инициатива отвечает на «что»: область, где живёт код и решение задачи. Полигоны моделей → модели;
  буферы земли → земля; алгоритм теней → тени;
- сквозное качество («какое»: скорость, кооп…) — не инициатива, а тег-аспект (`aspects` в
  workflow.json): задача остаётся в своей области и получает тег (`#perf`). В инициативу этого
  качества идёт только общее, без одной области (бюджеты и замеры, общий рендер);
- задача задевает две области — туда, где основная правка; вторая — тегом или `depends_on`;
- ни одна не подходит — без инициативы и вопрос пользователю в итоге; новую инициативу заводит
  только пользователь (или по его «да»).

## Журнал решений

Задача — место, где потом ищут, почему сделано так. Поэтому в ней:
- **Description**: слова пользователя дословно;
- **Decision** (раздел, если решение обсуждали): варианты, за и против, выбор и почему;
- **Notes**: каждое следующее слово пользователя по задаче — `note --by user` дословно, и
  твои выводы на старте («как понял, с чего начинаю») и по итогу.

Каждое событие журнала само получает id сессии Claude Code (`CLAUDE_CODE_SESSION_ID`) и
коммит; админка показывает у задачи её сессии и открывает расшифровку.

## Процесс pipeline

В проекте с `todo`/`qa` в workflow.json (шаблон `pipeline`) работай по
[references/pipeline.md](references/pipeline.md). Кратко:
- груминг: `Decision` (влияние на основы `.tasks/tech/pillars.md`, варианты, выбор), затем
  «да» пользователя → `todo`;
- `todo → in_progress`: аттестация `preflight` (сверка решения с кодом); не сходится — назад в
  backlog с вопросом;
- `review`: приёмка пользователем → `qa` (`--by user`);
- `qa → done`: только после **независимого аудита**. Нового агента (не fork) запускаешь с
  брифом `tasks audit brief`, его JSON-вердикт записываешь `tasks audit add` как есть. Аудит
  можно делать пачкой на несколько задач; после первого — только изменённого (`--since`);
- вики — источник правды: по ходу работы её не правят, правки — черновиком в раздел задачи
  `Wiki`; в вики он переносится только на `qa → done` (аттестация `wiki_applied`). Черновики
  других задач — не источник правды (pipeline.md, «Вики — источник правды»);
- правка (`size: tweak`, невидимая пользователю) идёт коротким путём `in_progress → done`;
- экономия (раздел «Экономия» в pipeline.md): зелёный = нет high/medium, один аудитор на пакет,
  механическое — модели подешевле, не больше двух исполнителей, повторяющаяся находка → проверка;
- хранители (если проект их завёл, `guardians` в project.json): владелец зоны — как правильно
  делать одну вещь во всём проекте, только он решает, как растёт её общее место. Груминг: каждый
  хранитель (свежий агент) говорит своё слово в ТЗ (`## Guardians`, гейт `guardians_asked`); Arch
  QA: один аудитор по списку хранителей, находка в зоне → детальное ревью вызванного хранителя, задача
  закрыта, когда приняли все вызванные. Аудит всего проекта (только по просьбе пользователя):
  каждый хранитель — свежий агент на пачку файлов — читает каждый файл и ставит отметку
  (`владелец` / `✓` / `✗` с находкой: почему и как правильно через общее место); вердикт как есть —
  `tasks guardian sweep add`, отметки — в `tasks code`, в брифе и в админке, задача из нарушения —
  `tasks audit task`. Уставы и формат — [references/guardians.md](references/guardians.md).

## Статусы по умолчанию

`icebox ⇄ backlog → in_progress → review → done`, плюс `cancelled` из любого статуса.
Префикс id по умолчанию — `BL` (`BL-0007`).
Гейты шаблона (настраиваются в `.tasks/workflow.json` конкретного проекта):

- `icebox` — отложенные задачи (`hold: true`): `next` их не предлагает, сам их не бери и не
  предлагай. `backlog → icebox` — когда пользователь сам сказал отложить. Вывести из icebox
  (в `backlog`) — только по явной просьбе пользователя про эту задачу (номер или описание):
  `move BL-N backlog --by user --note "<его слова>"` (гейты `user_confirmed` + `reason`);
- `backlog → in_progress`: все `depends_on` закрыты;
- `in_progress → review | done`: отмечены критерии (если они есть — их может и не быть),
  заполнен Result (по исходным словам пользователя: что сделано),
  **аттестация `architecture_review`** (письменный вердикт по вопросам целостности) и
  command-гейты проекта (сборка, проверки) — если настроены;
- откат назад, переоткрытие, отмена — с `--note` причиной.

Вопросы гейтов читай из вывода `tasks check`, не по памяти: в проекте они могут быть другими.

## Сценарий 1 — надиктовка

Пользователь говорит потоком (часто голосом, с оговорками и ошибками распознавания).

1. Разбей на **атомарные** задачи: одна задача = одна просьба/мысль пользователя.
   Порядок «сначала X, потом Y» → `depends_on`.
   **Иерархий нет** (жёсткое правило пользователя): эпик — не папка задач, а обычная задача,
   просто объёмная сама по себе (`size: epic`). Не заводи «эпик + дочерние задачи», не ставь
   `parent`. Большая мысль пользователя — одна задача размера epic: её слова целиком в
   Description, а шаги — в её собственном разделе Plan чек-листом (`- [ ] шаг`), который
   отмечаешь по ходу работы. Этого достаточно, чтобы наполнить эпик подзадачами. Отдельной
   задачей — только самостоятельная просьба пользователя (связь — `depends_on`, если важен порядок).
2. `title` — коротко, по делу (≤ 80 символов), без «нужно бы». Исправь явные ошибки
   распознавания речи по контексту проекта (имена модулей, экранов, терминов).
3. `description` — **дословные слова пользователя** в кавычках-ёлочках. Это и есть задача:
   вводные, от которых потом отталкиваются в работе, — не пересказ и не «улучшенная» версия.
   Своих переформулировок не добавляй. Можно отдельной строкой «Где в коде: …» — только
   факты (файлы, функции), без догадок о причинах и без «надо бы ещё».
4. `acceptance` — **по умолчанию пусто.** **НЕ ВЫДУМЫВАЙ требований** (жёсткое правило
   пользователя). Слова пользователя — это вводные: описание бага, идея, заметка, просьба.
   Описание бага — не критерий приёмки, идея — не критерий приёмки; **не превращай** их в
   чек-лист ни своими словами, ни его. Критерий пишется, только если пользователь **сам явно
   сформулировал** условие приёмки («готово, когда…», «должно…, проверь что…»). Никаких
   «не сломать X», «проверить на всех стадионах», «скриншоты на 4 размерах», «тексты на en
   тоже», смежных деталей. Как ты проверишь работу — твоё дело (Plan/Result). Неясно —
   спроси в итоге, а не дописывай. Задача без критериев — нормальная задача.
5. `initiative` — по разделу «Инициативы» ниже (если в проекте они есть).
   `type`/`priority`/`tags` выведи из слов («сломалось», «срочно», «когда-нибудь», «идея»);
   по умолчанию feature/p2. `--by user` — задачи надиктовал пользователь.
   `size` (если в workflow.json есть `sizes`) — твоя оценка объёма изменений, ставь всегда:
   `tweak` — правка (пара строк, текст, цвет, число), `task` — фича/баг (обычная доработка
   в одном-двух местах), `story` — заметная фича на несколько файлов/систем, `epic` — большая
   задача сама по себе: новая подсистема, перестройка, рефакторинг (это объём, а не группа задач). Разобрался в задаче по
   ходу работы и объём оказался другим — поправь `edit --size`.
6. Создай всё одной пачкой `add --stdin`, затем покажи итог короткой таблицей
   (id · заголовок · тип · приоритет · статус) и перечисли, что неясно и требует уточнения.
   Ничего не начинай делать по этим задачам, если пользователь не просил.

Перед созданием сверься с `tasks list --all` на дубли: похожая задача уже есть → дополни её
(`note`, `ac --add`, `edit`), а не плоди новую; скажи об этом в итоге.

## Сценарий 2 — работа «от задачи»

Когда в проекте есть `.tasks/` и пользователь просит нетривиальную работу:

1. **Найди задачу**: `tasks list` / `tasks list --all` по смыслу. Нет — заведи (`--by user`,
   если это его запрос): Description — его слова; критерии — только если он сам их назвал
   (см. п. 3–4 сценария 1). Работай от исходных слов пользователя в Description.
   Мелочь на пару строк и ответы на
   вопросы задачи не требуют.
2. **Возьми**: `tasks move BL-N in_progress`. Если задача уже `in_progress` — её ведёт другая
   сессия: не трогай, скажи пользователю.
3. **План** для заметной работы — `tasks section BL-N Plan --stdin`: шаги чек-листом `- [ ]`,
   отмечай выполненные (`section … Plan` с обновлённым списком). Подзадачи эпика живут здесь, а не
   отдельными задачами.
4. **По ходу** — `tasks note` на значимые открытия и решения (почему так, что отвергнуто).
   Нашёл работу вне рамок задачи — отдельной задачей в backlog, а не расширением этой.
5. **Финиш**:
   - отметь выполненные критерии `tasks ac BL-N --check …` (только реально выполненные и проверенные);
   - `tasks section BL-N Result --stdin`: что сделано, затронутые файлы, как проверено;
   - `tasks check BL-N review` — увидишь оставшиеся гейты и вопросы аттестации;
   - пройди ревью (ниже) и `tasks move BL-N review --attest architecture_review="…"`.
6. **done** — только после явного «принимаю/закрывай/ок, done» от пользователя:
   `tasks move BL-N done --by user`. Если пользователь заранее сказал «сделай и закрой» —
   можно сразу `in_progress → done` (гейты те же).

## Гейты — честно

- **Аттестация** — это настоящее ревью, а не формальность. Открой фактический diff
  (`git diff`, `git status`, изменённые файлы) и ответь по **каждому** вопросу гейта:
  `N. pass — доказательство (файл/функция)` или `N. fail — что не так`. Есть fail →
  не переводи: исправь, либо заведи задачу на хвост и тогда отвечай `pass — вынесено в BL-M`.
  Для крупных задач (много файлов, новая подсистема) отдай ревью субагенту со свежим
  контекстом: дай ему id задачи, Description/Acceptance, список файлов и вопросы гейта —
  его вердикт и идёт в `--attest`.
- **Command-гейты** запускают проверки проекта; упало — чини причину, а не гейт.
- **`--force`** — только по явной просьбе пользователя обойти проверку; всегда с `--note`,
  кто и почему разрешил. Сам гейты не обходи и workflow.json под задачу не ослабляй.
- Никогда не отмечай критерии, которые не проверены, и не пиши в Result того, чего не делал.

## Обзор для пользователя

- **«открой доску»** → живая доска в браузере. Пользователь команду не помнит и не должен —
  всё делаешь ты: `curl -s http://127.0.0.1:4747/api/board` и сравни `root` с корнем проекта.
  Совпало — админка уже работает, просто `open http://127.0.0.1:4747/tasks` (macOS; Linux — `xdg-open`).
  Нет ответа или другой проект — запусти фоном (`run_in_background`) `tasks serve --open`:
  сам возьмёт свободный порт и откроет браузер. Ответь одной строкой с адресом.
- «что в работе / покажи доску» → `tasks board`, перескажи кратко: что в работе, что
  ждёт ревью, что горит (p0/p1), что заблокировано.
- «что дальше» → `tasks next`, предложи 1–3 задачи с причиной.
- «что было с BL-N» → `tasks show BL-N` (файл + история переходов, аттестаций и проверок).

## Новый проект

1. `tasks init` в корне (создаёт `.tasks/`, правило `merge=union` для журнала в `.gitattributes`).
2. Настрой `.tasks/workflow.json` под проект: command-гейты на быстрые проверки
   (`{"kind":"command","run":"npm run lint","timeout_s":120}` и т.п., добавить id гейта в
   нужные `transitions[].gates`), проектные вопросы в `architecture_review.questions`
   (слои, где лежат данные/сохранения/локализация, какие dev-проверки гонять).
   Долгие проверки (полная сборка, e2e) — лучше вопросом в аттестации, чем command-гейтом.
   Есть `npm run check:i18n` (веб-игры) — гейт `"i18n": {"kind":"command","run":"npm run -s check:i18n",
   "timeout_s":60,"message":"npm run check:i18n упал — ключи локализации не сходятся"}` в переход
   `in_progress → review | done`; проектные вопросы — один пункт с префиксом «Проект:».
3. Добавь в `CLAUDE.md` проекта блок из [templates/CLAUDE.snippet.md](templates/CLAUDE.snippet.md) —
   так все сессии работают «от задачи».
4. `tasks validate`.

## Админка

`tasks serve [--port 4747] [--open]` — маленький сервер (только встроенные модули Node, только
чтение; писать — через CLI). Печатает адрес, по умолчанию `http://127.0.0.1:4747/`, занят —
берёт следующий порт; `--open` открывает браузер. Работает до Ctrl+C, запускать фоном.

Один инструмент (`ui/index.html` + `app.js`, виды `tasks.js`, `wiki.js`, `code.js`,
`session.js`, стили `app.css`), устроен по `.tasks/docs/ux-spec.md` проекта:
- **rail слева** — единственная навигация между разделами; разделы появляются, только если они
  есть в проекте: Задачи всегда, Вики — с `wiki` в `.tasks/project.json`, Код — с `code` или
  аудитами, страницы — из `pages`;
- **четыре зоны во всю высоту**: rail · навигация (дерево, 260 px, `[` прячет) · содержимое ·
  контекст выбранного (380 px, `]` прячет, Esc снимает выбор); ширины перетаскиваются;
- **выбор в адресе** (`?sel=…`), «назад» работает; ↑/↓ двигают выбор, Enter раскрывает,
  `/` — поиск в навигации.

Разделы:
- **Задачи** — доска по умолчанию (колонки открытых статусов, icebox/done/cancelled свёрнуты
  в полоски) или список строк по статусам; фильтры в дереве: «Ждёт меня» (review, backlog с
  Decision, вопрос исполнителя последней заметкой), «В работе», статусы, теги; карточка задачи
  справа: «Что дальше» (из переходов и гейтов workflow.json), сводка, слова пользователя,
  решение, план, обсуждение репликами, результат, история с сессиями; «развернуть» отдаёт
  тексты задачи всему содержимому;
- **Вики** — markdown из `wiki.dir`, дерево «лестницей»: разделы `##` домашней страницы →
  страницы → заголовки открытой страницы; справа связи страницы (ссылки, код, задачи);
- **Код** — техническая вики (`code.mjs`): обзор, основы, долг по находкам, файлы деревом с
  исходником и подсветкой мест, копии, аудиты; у файла — отметки хранителей из их обхода
  проекта (строка «Хранители»), их находки — причинами файла, как любые находки;
- **страницы проекта** (`pages`: `{id, title, url, start?, short?, icon?, embed?}`) — iframe на
  всё место справа от rail, к адресу добавляется `?embed=1` (кроме `embed: false`); не
  отвечает — одна строка, чем запустить (`start`);
- `/session/<id>` — расшифровка сессии Claude Code в содержимом, rail и задача остаются.

Сервер следит за файлами и шлёт server-sent events: изменения CLI видны через доли секунды,
без потери выбора и прокрутки, изменившиеся строки и карточки подсвечиваются. API:
`/api/project`, `/api/board`, `/api/wiki` (+ `doc`, `asset`, `search`), `/api/code` (+ `file`),
`/api/session`, `/api/stream`.

Интерфейсы читают те же файлы (или `tasks export`) и пишет через `scripts/lib.mjs`
(`createTask`, `moveTask`, `editTask`, `writeSection`, `editAcceptance`, `validateDb`, `exportDb`),
чтобы правила переходов и журнал были одни и те же.
